# B2.1_OBS Qualification Record

## Scope

This document records the qualification status of the Shelly TRV Gen1 experimental build:

```text id="mm8wfj"
B2.1_OBS
```

B2.1_OBS is the current long-term hardware-observation build used in the battery-drain investigation.

Its purpose is to combine the known qualified corrections from B2.1 with a low-intrusion PM52→cmd66 observer that can capture relevant host/radio state if a battery-drain event reappears.

This document records:

- build composition
- observer purpose
- software qualification
- noninterference design
- binary construction checks
- firmware identity
- hardware rollout
- current qualification limits
- release disposition

The qualification conclusion is:

```text id="0qr307"
B2.1_OBS RELEASE-CANDIDATE GO
```

This means:

> The build passed the defined offline/software qualification gates and is suitable for controlled long-term hardware observation.

It does not mean:

- production firmware
- final battery-drain fix
- battery-life certification
- complete root-cause proof

# 3. Why an Observer Was Added

Earlier testing established several important facts:

- stock 2.2.4 can enter frequent Beacon Recovery
- D3 `PS_MODE_ERROR` is not required for that Recovery behavior
- C-C removes the demonstrated stale-evidence recurrence
- fresh low estimator values can still occur
- host PM lifecycle defects exist independently of Beacon Recovery
- B2 ownership races can affect host sleep restrictions
- host-visible PM success does not prove physical WF200 sleep

The remaining problem is therefore event correlation.

If a corrected TRV develops rapid drain, it is not sufficient to know only:

```text id="96uiw0"
battery voltage dropped
```

The project needs to know what the host and WF200 control paths were doing around the first abnormal state.

---

# 4. Observer Objective

The observer is designed to correlate:

```text id="48qbb0"
PM52 host PM requests
```

with:

```text id="p86z77"
command 0x66 WF200 statistics
```

and with:

```text id="ft9vko"
A1R PM completion decisions
```

during the same connection/runtime context.

The observer is specifically intended to answer questions such as:

- What PM52 command was requested?
- What result was returned?
- How did A1R classify the completion?
- What cmd66 statistics were observed afterward?
- Was a fresh `real_beacon_skip` measurement produced?
- Did the connection epoch change?
- Was the observed state part of normal PM progression or a first-fault sequence?

# 17. B2 Defect

B2 is a shared reference counter representing active software owners that require the host to remain at EM1 or shallower.

Conceptually:

```text id="yt3l7o"
B2 = 0
no EM1 owner

B2 = 1
one EM1 owner

B2 = 2
two EM1 owners
```

Stock firmware contains a demonstrated preemption/lost-update race because relevant read-modify-write paths are not consistently serialized.

Possible consequences include:

```text id="xg03xn"
phantom contribution
```

or:

```text id="t84oat"
lost contribution
```

Both violate reference-count semantics.

---

# 18. B2 Correction

The correction applies bounded serialization around the complete relevant B2 read-modify-write operation.

It preserves:

```text id="h30atq"
reference-count semantics
```

It does not:

```text id="ynobn6"
force B2 = 0
```

and does not:

```text id="e67b8q"
convert B2 into a Boolean
```

This is important because multiple simultaneous ownership contributions are legitimate.

# 30. Connection Epoch Tracking

A PM/statistics observation can become misleading if values from different WLAN connections are combined.

The observer therefore tracks:

```text id="nw5hho"

```

This is especially relevant for:

- reconnects
- association changes
- statistics baseline changes
- PM state reinitialization

The observer can therefore distinguish:

```text id="cuhhkj"

```

from:

```text id="u0cnc5"

```

when interpreting PM52/cmd66 state.

# 32. First-Fault Freeze

The first-fault freeze is designed to preserve the earliest relevant abnormal sequence.

Without this behavior, a ring buffer could continue rotating and overwrite the events most closely associated with the initial fault.

Conceptually:

```text id="oyktfx"
normal event stream
       |
       v
first qualifying fault
       |
       v
freeze fault context
       |
       v
preserve evidence
```

This is particularly useful for battery drain because the device may remain running for hours after the first abnormal PM transition.

# 48. Observer Noninterference Limitation

Software-level noninterference can be tested extensively.

Absolute physical noninterference cannot be proven solely from static or behavioral software tests.

Even a small observer may theoretically alter:

- instruction timing
- cache/bus timing
- interrupt timing
- scheduling boundaries

Therefore the project explicitly distinguishes:

```text id="8gsgu9"
software noninterference qualified
```

from:

```text id="s0kwkp"
physical timing perturbation impossible
```

The latter is not claimed.

# Methodology Note

The qualification approach requires that each included correction be:

```text id="opkp3f"
demonstrated
+
safely correctable
+
independently qualified
+
composition-qualified
```

A build is not accepted merely because it boots.

Qualification includes behavioral tests, binary-difference review, deterministic reconstruction, independent container verification and controlled physical deployment.

Historical builds retain their original identities.

A1 results are not relabeled as A1R.

Historical B2 results are not relabeled as B2.1.

Observer instrumentation is not presented as a production fix.
